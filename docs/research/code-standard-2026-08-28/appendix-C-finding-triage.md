### Overall read

Roughly 6 of the 389 findings deserve a developer's afternoon; about 350 are real-but-mislabelled accessibility work; the rest is noise or context.

The headline is that the two ratings are telling you almost the opposite of what the team believes.

The reliability D is a category error, but not in the way the brief assumes. Yes, Sonar classifies accessibility rules as BUG/reliability, and yes that is misleading - unlabeled inputs and mouse-only click handlers have no runtime failure mode; nothing throws, no data is wrong. But the sharper point is arithmetic. Sonar's published rating grid sets the letter from the single worst issue, not the volume: Standard Experience is "A = 0 bug, B = minor, C = major, D = critical, E = blocker", and MQR mode is the same shape over LOW/MEDIUM/HIGH/BLOCKER impacts. I pulled the live severities: InputWithoutLabelCheck is MAJOR / RELIABILITY MEDIUM (ceiling C), MouseEventWithoutKeyboardEquivalent is MINOR / RELIABILITY LOW (ceiling B). Neither can produce a D at any count. So the D is caused entirely by one or more of the 8 issues nobody has looked at - the 3 C# and 5 TypeScript bugs listed as "rules unknown". The 330 accessibility findings that are consuming all the team's anxiety are contributing nothing to the rating, and the 8 that nobody has opened are contributing all of it. Say it to the team in one sentence: D does not mean 338 defects, it means one bad one, and you have not found it yet.

The security E is real and correctly earned. Security rating is "A = 0 vulnerability ... E = at least one blocker vulnerability", and you have four blockers. The brief under-weights the right one: tssecurity:S6105 at tenant-bootstrap.ts:65 is a taint-analysis result (source-to-sink, much harder to trigger spuriously than a pattern match) sitting in the file that resolves tenancy in an app where tenancy comes from the Host header and each office is a separate PHI database. Read that line before you read anything else on this list. The second under-weighted item is one Sonar itself under-rates: csharpsquid:S2068 on the seed contributors is only MAJOR/MEDIUM in Sonar's general-purpose scale, but in an ABP multi-tenant application "hard-coded credential in a data seed contributor" plausibly means a default admin password sitting in some subset of 11 tenant databases, days before anonymous internet traffic arrives. That is unauthenticated admin access to one office's complete PHI, and per-tenant database isolation does nothing about it because the attacker is legitimately inside a tenant.

On hotspots, the distinction the team is missing is that a hotspot is a question, not an accusation - Sonar's own words: "a security-sensitive piece of code is highlighted, but overall application security may not be impacted; it's up to the developer to review". They contributed zero to your E, because security_rating counts only vulnerabilities. They drive a separate metric, security_review_rating (A = 80% reviewed or better), where 0 of 31 puts you at E and trips the Sonar way condition new_security_hotspots_reviewed < 100%. "Review" is a defined three-step procedure, not open-ended analysis, and 31 of them is about three hours in one sitting with both developers at one screen - roughly 12 minutes for the first instance of each of ~10 distinct rules, then 1-2 minutes each for repeats. It is a half-day once, not a programme. The 6 csrf hotspots are very likely false positives on your bearer-token API surface - Microsoft's antiforgery docs say CSRF is a cookie-credential problem and that bearer tokens are protection against it, and ABP applies AbpAutoValidateAntiforgeryToken globally while deliberately bypassing non-browser bearer clients - with the genuine exception of the AuthServer's cookie-authenticated Razor Pages, which is exactly the surface about to face the internet. Verify that class with one curl (cookie, no antiforgery token, expect rejection) rather than by triaging six items separately.

Underneath all of it is the setting nobody flagged: new code = previous_version pinned at 2026-04-15 means new code is the entire project, and the Sonar way gate's four conditions - 80% coverage, under 3% duplication, 100% hotspots reviewed, zero violations - are being applied to all 80k lines at once. That gate is unpassable and will stay unpassable, which is precisely how a two-person team learns to ignore a tool. It is also why signal and noise are indistinguishable: with no new-code boundary, every finding ever written arrives simultaneously with equal weight. Change it to Number of days = 30 - not "previous version done properly", because that requires incrementing sonar.projectVersion on every analysis and two SDE 1s shipping continuously will not sustain it, and the setting will rot straight back to today's state. Note that PR analysis is unaffected: Sonar applies only new-code conditions to a PR diff, so your PR decoration is already a working clean-as-you-code gate. Gate merges on that, and treat the main-branch rating as a trend you watch rather than a wall you climb.

**C1.2 `CONTEXT-DEPENDENT` -- Web:InputWithoutLabelCheck (RSPEC-1097)**

- Rule name: "input", "select" and "textarea" tags should be labeled
- Count in repo: 253, concentrated in 10 files (47 internal-appointment-detail, 26 people-edit-modal, 17 patient-profile-redesign, 13 appointment-add-claim-parties-section)
- Launch-blocking: **no** | Effort: 30 min sampling; then whatever the real remainder is, absorbed into normal work at 5 min each
- Source consulted: <https://raw.githubusercontent.com/SonarSource/sonar-html/master/sonar-html-plugin/src/main/resources/org/sonar/l10n/web/rules/Web/InputWithoutLabelCheck.html>
- What it detects: Every input (except submit/button/image/hidden), select and textarea that has no associated label. Satisfied by a <label for> matching the control's id, or by aria-label / aria-labelledby on the control. Explicit documented exception: implicit labels (a <label> wrapping the control) do NOT raise an issue. Tagged accessibility + wcag2-a. Type BUG, MAJOR, RELIABILITY MEDIUM, 5 min remediation each. Cites W3C H44 and WCAG 2.2 SC 1.3.1.
- Reasoning: Two things are true at once and the team is conflating them. (1) It is a category error to call this a reliability bug. The rule's own text is entirely about screen readers and motor-impaired users; there is no runtime failure mode, nothing throws, no data is wrong. Sonar's taxonomy puts accessibility under BUG/RELIABILITY because the code is 'incomplete' relative to its intent, not because it crashes. Read as 'runtime defects', 253 is a false alarm. (2) It is NOT noise as an accessibility finding. Unlabeled form controls fail WCAG 2.2 SC 3.3.2 Labels or Instructions, which is Level A - the floor, not the aspiration - and SC 1.3.1 and 4.1.2 alongside it. For a US healthcare-adjacent portal where four external user roles self-register from the public internet, Level A form labelling is the part of accessibility that most reliably turns into a complaint. But before anyone fixes 253 of them, one specific false-positive cluster has to be ruled out: the analyzer parses the Angular template statically. An Angular Material control written as <mat-form-field><mat-label>X</mat-label><input matInput ...></mat-form-field> has no for/id pair and no aria-label in the template - Material generates the association at runtime - so Sonar flags it while the rendered DOM is actually correct and accessible. Given 47 hits in a single detail component, that pattern is the most probable explanation for the bulk of the 253.
- Action: Do not bulk-fix and do not bulk-suppress. Spend 30 minutes: open the top file, pick 5 flagged controls, run each through the browser accessibility tree (Chrome DevTools > Elements > Accessibility pane) and read the computed Name. If Name is populated, that instance is a false positive and the whole Material-wrapped class of them is too - mark that subset Won't Fix with the one-line justification 'label association generated at runtime by mat-form-field; verified in the a11y tree', and record the reasoning once so the next person does not redo it. Whatever is left with an empty accessible name is a genuine Level A failure - fix those, at 5 minutes each, in the files you are already touching for feature work rather than as a 253-item campaign. Do not deactivate the rule: it is worth keeping switched on for new templates. If most of the 253 turn out to be Material false positives, that is also the argument for adding axe-core to the component test run, which measures the rendered DOM and does not make this mistake.

**C1.3 `LIKELY-REAL-NEEDS-REVIEW` -- Web:MouseEventWithoutKeyboardEquivalentCheck (RSPEC-1082)**

- Rule name: Mouse events should have corresponding keyboard events
- Count in repo: 77
- Launch-blocking: **no** | Effort: half a day if the 77 reduce to 5-8 repeated patterns, which is the usual outcome
- Source consulted: <https://raw.githubusercontent.com/SonarSource/sonar-html/master/sonar-html-plugin/src/main/resources/org/sonar/l10n/web/rules/Web/MouseEventWithoutKeyboardEquivalentCheck.html>
- What it detects: onClick with no onKeyDown/onKeyUp, onMouseover with no onFocus, onMouseout with no onBlur. The current rule text explicitly recognises Angular bindings - (click), ng-click, on-click - and skips anything the analyzer does not recognise as a native HTML element, i.e. custom components are not checked. Native interactive elements are exempt: <button>, <a>, <summary>, input type=button/submit, and controls with implicit textbox/checkbox/radio/listbox roles. An issue IS still raised on anything carrying role="button". Type BUG, MINOR, RELIABILITY LOW, 5 min. Cites WCAG 2.2 SC 2.1.1 Keyboard and techniques SCR2/SCR20/SCR29.
- Reasoning: This one has a much better signal-to-noise ratio than the label rule, because of what the rule explicitly skips. It does not fire on <button> or on <a href>, and it does not fire on custom components. So a hit means a (click) sitting on a genuinely non-interactive native element - a div, td, tr, span, i - which really is unreachable by keyboard unless the template also supplies tabindex and a key handler. That is a WCAG 2.2 SC 2.1.1 Level A failure and, unlike the label case, it is not a static-analysis artifact: the rendered DOM will be just as unreachable as the template. The rule text also warns about the one exemption that leaks - <a onClick> with no href is exempted by the tag check but behaves as inert text from the keyboard - so the true count may be slightly higher than 77, not lower. Still only LOW reliability impact, so it contributes nothing to the D. It is a real accessibility defect class carrying a misleading label.
- Action: Triage by element, not by occurrence. Grep the templates for (click) on div/span/td/tr/i and sort by what the handler does. Anything that is the only way to perform an action - opening the appointment detail, selecting a claim party, submitting - is a keyboard trap for a real user and should be converted to a <button> with button styling reset, which fixes the finding and the roles and the focus ring in one edit. Anything that is a convenience duplicate of a control that also exists as a button is genuinely low priority. Expect the 77 to collapse to a much smaller number of distinct repeated patterns (a clickable table row, a clickable card) - fix the pattern once in the shared component and the count drops in bulk.

- Launch-blocking: **yes** | Effort: 30 min to read and trace; 1-3 hours to fix properly with an allow-list

**C2.5 `LIKELY-REAL-NEEDS-REVIEW` -- cs/log-forging**

- Rule name: Log entries created from user input
- Count in repo: 2 MEDIUM, both in ExternalAccountAppService.cs
- Launch-blocking: **no** | Effort: About 1 hour for the 2 alerts plus enabling CA2254. The associated PHI logging policy is another 1-2 hours of writing and grepping, and is the part with lasting value.
- Source consulted: <https://codeql.github.com/codeql-query-help/csharp/cs-log-forging/>
- What it detects: Query help: 'If unsanitized user input is written to a log entry, a malicious user may be able to forge new log entries.' @security-severity 6.1, @precision high, tag external/cwe/cwe-117, in the default suite. From LogForgingQuery.qll: SOURCE is `ThreatModelSource instanceof ActiveThreatModelSource` (untrusted input per the configured threat model - by default, remote/HTTP request data). SINK is `LogForgingLogMessageSink` - an argument to a call to a method on a logger class, excluding arguments to source-defined extension methods (those are followed interprocedurally instead). SANITIZERS are exactly three: HtmlSanitizer (HtmlSanitizedExpr), StringReplaceSanitizer (calls to String.Replace, String.Remove, String.ReplaceLineEndings, or Regex.Replace), and GuidSanitizer (GuidSanitizedExpr - a GUID is inherently injection-safe). The recommended fix in the query help is `username.Replace(Environment.NewLine, "")`.
- Reasoning: Answering (b) in two parts. PART 1 - does the rule distinguish log forging from PHI-in-logs? No. It is purely CWE-117 and it is source-driven: it fires on data that came from an HTTP request, regardless of whether that data is sensitive. It has no PHI concept whatsoever. The complementary rule, cs/exposure-of-sensitive-information, is sink-compatible but source-different - it fires on name-matched private data regardless of whether it came from a request. So the two rules cover two orthogonal halves and neither covers the intersection you actually care about, which is 'request-supplied PHI reaching a log'. That intersection is CWE-532, and there is no dedicated C# CodeQL query for it in the default suite. Concretely: on the same two lines in ExternalAccountAppService.cs, log-forging is telling you an anonymous registrant can inject CRLF and forge audit lines; nobody is telling you those same lines will be writing self-registration form contents - which for your four external roles will include names, addresses, phone numbers and claim references - into log files that then flow to whatever aggregator you pick. In a HIPAA system, log files are a PHI store: they need the same retention, access control, and BAA coverage as the database, and every unnecessary field in them expands that footprint permanently, because logs are the one datastore nobody ever goes back and purges. PART 2 - is structured logging the fix? For the PHI problem, partly. For the CodeQL alert, NO, and this is the trap. Switching `_logger.LogInformation($"Registering {email}")` to `_logger.LogInformation("Registering {Email}", email)` is unambiguously the right .NET practice - Microsoft Learn's library-authoring guidance says 'Avoid string interpolation in logging' and points at analyzer rule CA2254 'Template should be a static expression', and the message-template form is what lets providers 'store the parameter values as fields' - but the tainted value is STILL an argument to a logger method, so it is still a LogForgingLogMessageSink and the alert will not clear. Worse, for the newline-injection risk it only helps if your sink actually stores fields (Serilog to a structured sink, JSON console); with a plain text file formatter the value is still concatenated into a line and CRLF still splits it. Do not let anyone tell you 'we moved to structured logging, the alert is a false positive'. The change that clears the alert AND fixes the injection is the one the query help gives: sanitize the value before it reaches the logger, i.e. `.Replace(Environment.NewLine, "")` or better `.ReplaceLineEndings(string.Empty)` (both are recognised sanitizers), or replace the user string with a GUID/entity id (also recognised).
- Action: Fix, do not dismiss - it is two lines. For each of the 2: (1) convert to a message template with named placeholders, not interpolation, since that is correct regardless; (2) sanitize the tainted argument with `.ReplaceLineEndings(string.Empty)` before passing it, or drop the raw value for the entity id, which clears the alert properly. Then the durable part, which is the real recommendation: turn on CA2254 as a build warning solution-wide so interpolated log templates stop appearing (this is a first-party analyzer, zero new tooling, and a two-person team can sustain it), and write down a one-paragraph 'what must never be logged' rule referencing the OWASP list - passwords, tokens, session ids, connection strings, keys, and health/PII - as the only logging standard you maintain. If you later want mechanical enforcement rather than discipline, .NET has a first-party answer: Microsoft.Extensions.Compliance.Redaction plus Microsoft.Extensions.Telemetry, where you call builder.EnableRedaction(), tag parameters on [LoggerMessage] methods with a data classification, and the value is redacted before it is written ('User SSN: *****' in Microsoft's own example). I would NOT adopt that now - it is a real refactor of every log call site and the HmacRedactor is still marked experimental (EXTEXP0002). Note it as the thing you adopt if a compliance audit ever demands proof rather than policy.

The email-template HTML suppressions are the ones I would look at hard, because HTML rules suppressed on email templates can mask injection and escaping problems, and this application emails content around workers'-comp medical examinations -- content adjacent to PHI, rendered by mail clients you do not control. The category-level point that applies to all 19: a suppression is a claim that a finding is not worth acting on, and that claim can only be evaluated against a gate that is enforced. Since the Sonar gate cannot fail and has been red for weeks, none of these suppressions has been meaningfully justified for months -- they are unreviewed assertions attached to an unenforced control, which is why they belong in a removal review even though some should survive it.

If you keep Sonar: re-run analysis with all 19 disabled, delete every suppression whose rule no longer fires (dead suppressions cost nothing to remove and there will be several after 465 commits), then hand-review the email-template HTML entries specifically and require a one-line justification comment on each survivor. Budget one afternoon, not a project. **C3.20 `LIKELY-REAL-NEEDS-REVIEW` -- wildcard CORS header on a dead endpoint**

- Rule name: Access-Control-Allow-Origin: * on an unused route
- Count in repo: 1 endpoint (as reported)
- Launch-blocking: **yes** | Effort: 2-4 hours including the grep and the allowlist check
- Source consulted: <https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS>
- What it detects: Nothing. It is a permissive header left on an endpoint no longer in use.
- Reasoning: Worth being precise about the actual exposure rather than overstating it. Per MDN's CORS documentation, the wildcard works only for requests without credentials: 'When responding to a credentialed request, the server must specify an origin in the value of the Access-Control-Allow-Origin header, instead of specifying the * wildcard', and if a request carries a Cookie header while the response has the wildcard, 'the browser will block access to the response, and report a CORS error in the devtools console'. So this is not a direct credentialed-read vulnerability -- the browser refuses the combination. The reasons it still must go are three. It exposes whatever the dead endpoint returns to any origin for unauthenticated reads, and 'dead' endpoints are frequently still routed. It is a template: the next developer adding a CORS policy copies the existing one, and this codebase resolves tenancy from the HTTP Host header alone, making origin handling security-relevant in a way it is not in a single-tenant app. And it produces a false negative in review -- a reader sees CORS configured and moves on. Dead code carrying a permissive security header is the specific combination that survives audits, because nobody tests what nobody calls.
- Action: Delete the endpoint, not just the header -- an unused route on a service about to face the public internet is attack surface regardless of its CORS policy. Then grep the solution for other `*` CORS values and for the ABP CORS origins configuration, and confirm the real API uses an explicit per-tenant origin allowlist. Given host-header tenancy, that allowlist is genuinely load-bearing and deserves a test.

**C3.24 `REAL-EXPOSURE` -- branch protection: enforce_admins: false with 1 required review on a single-author repo**

- Rule name: Merge gate that is advisory by configuration
- Count in repo: 1 ruleset
- Launch-blocking: **yes** | Effort: 1 hour for the settings; gated on the test-job work above
- Source consulted: <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches>
- What it detects: Claims code review and protected-branch enforcement on main.
- Reasoning: The setting that makes everything else on this list moot. GitHub's protected-branches documentation describes the enforcement option as overriding the default in which 'the restrictions of a branch protection rule do not apply to people with admin permissions'. With enforce_admins false on a repo where both developers are almost certainly admins, every protection is advisory -- which is consistent with the observed reality that Sonar has been red on main since 2026-07-08 and cascade merges proceed as named bypasses.
