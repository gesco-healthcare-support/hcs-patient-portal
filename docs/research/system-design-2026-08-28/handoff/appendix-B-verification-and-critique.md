## tenancy-data

Verdict: **material-errors**. Claims checked: 40.

### Material errors (5)

- CLAIM 24 IS WRONG ON ITS STATED THRESHOLD. QueryStringTenantResolveContributor is NOT at index 0 of the composed resolver chain. AbpAspNetCoreMultiTenancyModule depends on AbpMultiTenancyModule, whose ConfigureServices runs first and executes `options.TenantResolvers.Insert(0, new CurrentUserTenantResolveContributor())`. In the assembled AbpTenantResolveOptions, index 0 is CurrentUserTenantResolveContributor (which reads the tenant from the CURRENT USER'S TOKEN CLAIMS), and QueryString/Route/Header/Cookie occupy indices 1-4. This is material, not cosmetic: the first two capability requirements demand that tenant identity be derivable only from the host name and that a token from one office not authorise a request for another. The resolver that actually runs first reads the access token, before any domain resolver. Any design conclusion built on 'the domain resolver only has to beat the query-string resolver' is unsound.

- CLAIM 27 IS WRONG AND ITS QUOTATION IS NOT ON THE CITED PAGE. The ABP docs page at abp.io/docs/latest/framework/architecture/multi-tenancy shows only `options.AddDomainTenantResolver("{0}.mydomain.com");` and never describes it as a shortcut for `TenantResolvers.Insert(0, ...)`. The actual implementation (framework/src/Volo.Abp.AspNetCore.MultiTenancy/Volo/Abp/MultiTenancy/AbpMultiTenancyOptionsExtensions.cs) is `options.TenantResolvers.InsertAfter(r => r is CurrentUserTenantResolveContributor, new DomainTenantResolveContributor(domainFormat))` -- InsertAfter the current-user resolver, i.e. index 1, NOT Insert(0). The class name is also wrong: it is DomainTenantResolveContributor, not DomainTenantResolver. Consequence: even the stock helper does not make the domain a hard first boundary; the token-claim resolver still precedes it.

- CLAIM 23 ATTRIBUTES A QUOTATION TO A PAGE THAT DOES NOT CONTAIN IT. ABP 10.2 and 10.3 are past releases, not the current stable and the roadmap item. - CLAIMS 3 AND 5 TOGETHER MISSTATE THE EVIDENCE STATUS OF AWS SOURCES. Claim 5 flags only the SaaS Tenant Isolation Strategies whitepaper as 'historical reference only'. # Appendix B2: completeness and portfolio critique

## The three decisions, as the critique ranked them

- 1. PROVE AND PIN THE TENANT BOUNDARY - AND TREAT IT AS THE GATE ON EXPOSURE. Run the curl matrix: __tenant as query string, route value, header and cookie against all three hostname shapes; a token minted at office A presented to office B's API; and an untyped IDistributedCache write observed for the t:{tenantId} prefix. Then make all three permanent automated tests, and add the null-tenant guard so a tenant-scoped background job refuses to run rather than resolving to the host database. WHY FIRST: this is the only failure in the entire body whose consequence is one practice's injured worker appearing in another practice's data, or in the host database - a disclosure that no edge hardening, no backup and no monitoring can undo or even detect after the fact. It is also the cheapest item in 1,000 hours of recommendations: hours, not weeks. Three separate areas independently identified it as the highest-value action and were independently right. If it fails, nothing else on this list matters until it is fixed; if it passes, the design's central claim is real rather than intended.

- 2. DENY BY DEFAULT AT THE EDGE AND TAKE THE ADMINISTRATIVE PLANE OFF THE INTERNET ENTIRELY. A default_server on 443 that terminates unmatched SNI and Host (closing the bare-apex-to-AuthServer and api.<base>-to-SPA fallthroughs); no /hangfire route at the edge at all, independent of the planned code fix; admin, health-UI, metrics and the object-store console bound to an unpublished second listener reached by SSH local forward; the missing security response headers and TLS pinning; stripping of every alternative host header inbound; and Docker network segmentation so the static-file container can no longer open a socket to SQL Server. WHY: this is roughly 20-30 hours for the single largest reduction in attack surface available, it is almost entirely configuration with no ongoing obligation, and every one of its failure modes is a hard error somebody notices immediately. Note the deliberate exclusion: NOT the full FallbackPolicy across both processes - that is the expensive half, it can break sign-in on a system with no staging, and it should follow once the endpoint inventory has run clean as a report for a month. Also note the resolution the body never states: the edge validates label SHAPE, the application validates MEMBERSHIP, so that adding an office still touches nothing at the edge.

- 3. ONE OFF-BOX, IMMUTABLE, ACTUALLY-RESTORED RECOVERY PATH COVERING THE OBJECT STORE AS WELL AS THE DATABASES - WITH AN ALERT ON THE ABSENCE OF A RECENT VERIFIED RESTORE. Backups written off the VM under a credential that can write but not delete, into storage with retention the writer cannot shorten; the OpenIddict certificate and passphrase, the DataProtection key ring and the secrets set recoverable independently of the box; the MinIO contents included, not just SQL; and one timed restore performed and recorded before go-live. WHY: today the system has no recoverable state at all - backups default to the same disk and no restore has ever been attempted - so every other risk in the body currently resolves to permanent loss. The absence alert is what converts this from a control that decays silently into one that fails loudly, and it costs about two hours. AND THE DECISION EMBEDDED IN THIS ONE: do not onboard a real practice until 1-3 hold. Every property that makes this programme executable by two SDE 1s - free downtime, destructive rehearsal in production, rollback by discarding rather than reconciling, no BAA on the critical path - is a property of the no-PHI window, and it is spent the moment the first real booking exists. The sequencing of the business is itself an architectural decision, and it is the one that decides whether the other two are cheap or impossible.

## Internal contradictions across the fourteen areas

- REDIS EVICTION POLICY: THREE AREAS, THREE INCOMPATIBLE VALUES ON ONE CONFIG KEY. state-session says set maxmemory-policy to allkeys-lru and turn AOF off, making Redis a pure disposable cache. scaling-topology REQUIRES maxmemory-policy be noeviction or volatile-*, and MUSTs that the key-ring store cannot evict. capacity-model MUSTs that any store holding session-critical key material be free of memory-pressure eviction. These reconcile only if state-session's key-ring move to SQL lands FIRST; state-session says so, but the other two areas' requirement lists are written as unconditional MUSTs and will be read as such. Applying allkeys-lru before the key ring moves silently destroys DataProtection keys under memory pressure.

- WHERE THE DATAPROTECTION KEY RING LIVES - AND MIGRATION-PATH'S WHOLE PHASE 3c DEPENDS ON THE ANSWER. state-session moves the ring to the host SQL database. secrets-config's Tier 3 is written on the premise that 'the system persists it to an explicit location (Redis)'. migration-path Phase 3c builds its most vivid risk argument - claimants' and attorneys' email-confirmation links dying, a human conversation per recipient - entirely on the ring being in Redis, and specifies RDB copying and REPLICAOF to move it. If state-session's change lands, Phase 3c's central hazard evaporates and its mechanics are wrong; if it does not, state-session's AOF-off recommendation is destructive. availability-dr meanwhile MUSTs the keyring be recoverable independently of the primary host, which the host SQL database on the same VM does not satisfy until backups are off-box. Four areas, three mutually exclusive mental models of one artefact.

- TOTAL SETUP COST EXCEEDS THE BUDGET BY AN ORDER OF MAGNITUDE, AND EVERY AREA CLAIMS AFFORDABILITY INDEPENDENTLY. Summing the stated setup ranges: 742-1,090 developer-hours. At ~40 hours/month of infrastructure time that is 18-27 months with zero feature work, against a brief that says a code-standard exercise already claims a large share. ## Under-weighted risks

- PARTIAL ADOPTION IN AN UNPLANNED ORDER IS THE MOST LIKELY OUTCOME, AND SIX AREAS INDEPENDENTLY IDENTIFY IT AS WORSE THAN DOING NOTHING - a half-landed FallbackPolicy that breaks sign-in, a half-executed Phase 3 with state in one place and compute in another, a staging environment built before the deploy is fail-fast, an archive written but never verified, capacity data collected but never read, backups produced but never restored. Nobody wrote the portfolio-level 'if you only get 40 hours, do exactly these' list, so the order will be chosen by whichever document a developer opens first. This risk is created BY the research body, not merely missed by it.

- THE AMBIENT-NULL-TENANT HAZARD IS TREATED AS A TESTING CONCERN RATHER THAN AS A LIVE DEFECT. A recurring job whose argument carries no tenant resolves to the HOST database. Twelve jobs iterate offices; three run every fifteen minutes. That is office-shaped data being written into the wrong database, silently, right now, in a system whose entire isolation story is 'one office, one database'. It deserves the same status as the untested __tenant resolver - a fifteen-minute check and a hard guard - and instead it appears as one MUST about idempotency.

- SHARED-CACHE CROSS-TENANT LEAKAGE IS UNDER-RATED RELATIVE TO ITS SEVERITY. state-session notes in passing that typed IDistributedCache<T> prefixes keys with t:{tenantId} but UNTYPED USAGE DOES NOT, and asks for a test. A single untyped cache write of a permission grant or a settings blob is a cross-office authorisation leak with exactly the same blast radius as the resolver bug, and it will not produce an error - it will produce office A's user holding office B's permissions. This belongs beside the resolver curl test as a go-live blocker, not in a SHOULD.

- TIME-TRIGGERED FAILURES ARE THE ONE CLASS THAT ARRIVES WITH NO CHANGE TO BLAME, AND THE BODY KEEPS ADDING TO THE INVENTORY. Already: the OpenIddict PFX. Added by the recommendations: a DataProtection wrapping certificate, a standby signing certificate refreshed annually, per-office TDE certificates (N of them, growing with the fleet), wildcard certificates at three depths, and a backup-encryption certificate. Certificate maximum lifetimes are on a published downward schedule, which network-exposure correctly flags. secrets-config MUSTs 30-day expiry notice; nothing in any area implements the mechanism that would produce it, and no area owns the register.

- THE OBJECT STORE IS THE SYSTEM'S LARGEST UNPROTECTED ASSET AND ITS MOST EXPOSED UNMAINTAINED COMPONENT AT THE SAME TIME. It holds the actual medical documents and packets, has no backup design anywhere in the body, sits on the same disk as the database and the current backup directory, is published to the internet at minio.<base>, is authenticated to as root by the application, and - per scaling-topology's own finding - its open-source server is archived with no patch stream. Three areas build NEW dependencies on it (backup target, migration transport, partner surface) without anyone reconciling that with the archived-upstream finding.

- DEPLOY-TIME IS THE DOMINANT AVAILABILITY RISK, NOT HARDWARE. Manual SSH, no staging, no CD, migrations that run on every bring-up against every office, an nginx force-recreate step, and a mandatory command-line flag. The body fixes the two documented traps, which is right, but never states that the most probable cause of the next outage is a Tuesday afternoon deploy by one of two people - and never proposes the cheapest controls for that: a declared change window, a two-person rule for production changes, and a written rollback plan attached to each deploy. Instead it adds a great deal of NEW deployment surface.

- MISDIRECTED EMAIL IS A REPORTABLE DISCLOSURE, AND THE ADDRESSING LOGIC IS TREATED AS A RESTORE ARTEFACT. Ex-parte-safe addressing - one primary recipient with specific others CC'd - is a compliance control implemented in application code, sending PHI to attorneys and adjusters. The body discusses duplicate sends only as a consequence of restoring or of running two tiers. Nobody proposes a test of the recipient-selection logic, a review of the CC construction, or an alert on outbox age. A single wrong CC is a breach with a 60-day clock, and it is far more likely than the VM dying.

- 'ALERTING' HAS NO HUMAN ON THE END OF IT. Multiple areas require alerts that must 'reach a human' within declared windows, including availability-dr's absence alert, which it calls the single most important line item it has. There is no on-call rotation, no escalation path, no second responder, and two people who may both be asleep or on leave. The dead-man's switch detects that the alerting path died; nothing detects that the recipient did not read it. The honest position - business-hours best-effort, with a stated maximum time-to-notice - should be written down and offered to practices, because it is what will actually happen.

- THE EDITION DECISION IS A LEGAL GO-LIVE BLOCKER BEING TREATED AS A LATER PLATFORM CHOICE. Developer edition includes all Enterprise functionality but is licensed for development and test, not as a production server (Microsoft Learn, editions-and-components-of-sql-server-2022, accessed 2026-08-31). Everything the team has built and measured has run with Enterprise features silently available. On Standard, verified from the same source: Resource Governor is unavailable (so tenancy-data's per-tenant resource-limiting requirement resolves to 'accept that none exists'), Always On availability groups are unavailable and Basic AGs carry one database each (confirming scaling-topology), and online page and file restore is unavailable (so piecemeal restore is offline). Buffer pool caps at 128 GB and compute at 4 sockets/24 cores, both comfortably above the current VM. Backup compression, encrypted backup, TDE, snapshot backup and backup/restore to S3-compatible storage over REST are all present on Standard, so the DR design survives - but nobody has run sys.dm_db_persisted_sku_features, and it will not catch runtime-only Enterprise features.

- AUDIT DISK EXHAUSTION IS A HARD, DATED FAILURE AND THE CHEAPEST MEASUREMENT OF IT IS BURIED. Over 100 audit rows per appointment, nothing pruning, ~9.7 GB free, and the audit tables, the database files, the object store and the current backup directory all on the same disk. capacity-model correctly identifies that a single daily df sample yields a projected exhaustion date within two weeks - the most decision-relevant number the team could hold - and it appears as a fallback at the end of one area rather than as a portfolio-level first action.

- REHEARSAL-SCHEDULE INFLATION MEANS ZERO REHEARSALS. Seven distinct recurring rehearsal obligations across the body, several described as non-negotiable by their own areas. When a team can afford one, and the body does not say which one, the outcome is none - and every area's threshold analysis then reads on the wrong side of its own line.

- CALIFORNIA AND STATE-LAW EXPOSURE IS ENTIRELY ABSENT. The body cites CFR extensively and argues carefully about federal retention clocks, while the product is California workers' compensation handling California medical records. CMIA (Civil Code 56 et seq.) and California breach-notification law impose obligations that differ from and can exceed HIPAA, and DWC/QME record rules bear on the retention question the body spends the most effort on. A verification pass that caught a misread statute once should be pointed here next.

## Areas the body missed

- NO AREA OWNS CI ITSELF. At least seven areas bill a MUST against a continuous-integration pipeline (has-pending-model-changes for both DbContexts x3 areas, secret scanning, endpoint-inventory test, PII-log grep test, export round-trip test, Testcontainers harness). Nothing in the body establishes that this team HAS CI, who builds it, or what it costs. Seven areas are drawing on a shared asset nobody costed or owned. If there is no CI, roughly a third of the body's cheapest controls do not exist.

- THE PACKET RENDERER IS UNGOVERNED. The Python/Flask renderer appears only as a throughput ceiling in scaling-topology and capacity-model. No area treats it as a component: it processes PHI documents; it is a second language runtime with its own dependency and CVE stream; the auth between API and renderer is unspecified; whether it writes PHI to container temp storage and whether that is cleaned is unspecified; its 2-worker concurrency is a fleet-wide, non-tenant-isolated shared resource with no per-office fairness. Every area's threat model stops at the .NET boundary.

- THE OBJECT STORE HAS NO BACKUP DESIGN. Every DR hour in the body targets SQL Server. MinIO is treated as a backup TARGET (availability-dr, migration-path) and as a deletion target (tenant-lifecycle), never as a backup SUBJECT. The actual medical documents, packets and joint declarations live there, on the same disk with ~9.7 GB free, with no versioning, no replication and no restore procedure. A restored database references objects that no longer exist; nobody can restore the objects.

- THE ANONYMOUS UPLOAD PATH IS UNDESIGNED. An unauthenticated public endpoint accepts files from claimants, attorneys and adjusters into a PHI system. Rate limiting is mentioned; nothing else is. No malware/content scanning, no MIME/extension validation, no per-request or per-day size cap, no quarantine before the file becomes an appointment document, no design for serving that file back to staff (content-disposition, sandboxing), and no disk-quota interaction with the 9.7 GB of free space. This is simultaneously the most likely initial compromise vector and the most likely disk-exhaustion vector, and it is nobody's area.

- AUTHENTICATION AND AUTHORIZATION DESIGN BEYOND TENANCY. Nothing covers the permission/role model, MFA for staff, refresh-token and session lifetimes (only the 15-minute access token is known; refresh token lifetime is never asked about), automatic logoff (45 CFR 164.312(a)(2)(iii), addressable), password policy, account lockout, or break-glass access. The brief names a REAL, RECURRING SUPPORT INCIDENT - same email holding a host account and an office account with separate hashes, subdomain-scoped reset - and no area proposes an identity design that fixes it. admin-surface deals with where admin endpoints listen, not with who may do what.

- THE ANGULAR SPA IS ABSENT AS A SURFACE. 87 components and 45 routed paths, and no area covers: whether the SPA can actually run under the CSP that network-exposure MUSTs (ABP's dynamic application-configuration and Angular's inline styles are the usual blockers, and a CSP that breaks the SPA will be deleted rather than fixed); where tokens live in the browser; cache-control on index.html versus hashed bundles, which is the classic post-deploy breakage; client-side error collection (there is none anywhere in the observability plan); and SPA/API version skew during a rolling change. The whole body reasons about the request path only from the proxy inwards.

- EMAIL AS AN EXTERNAL SYSTEM. Email is called the spine of the external-party workflow and appears only as something not to duplicate during a restore. Missing: SPF/DKIM/DMARC on the sending domain and how they interact with the DNS work in network-exposure and migration-path Phase 2; bounce and complaint handling; relay reputation and per-hour send limits against a 33-office fan-out; alerting on outbox age or depth (the three sanctioned alerts do not include it); and - the compliance point - that ex-parte-safe To/CC construction is a SAFETY-CRITICAL FUNCTION whose failure is a reportable disclosure under 45 CFR 164.402, yet no area proposes a test for it.

- OUTBOX AND PARTNER-INTEGRATION CORRECTNESS. Two durable outboxes carry the system's external effects. availability-dr and migration-path both DEPEND on idempotent redelivery with a partner-visible dedupe key, but no area owns the outbox design: retry/backoff, max attempts, poison-item quarantine, ordering, or an alert on stuck items. Nor does anyone own the Case Tracker contract: schema/version drift between two independently deployed systems, the lifecycle of the reconcile token this application issues to the partner, or what a multi-day partner outage does to a fail-closed ledger.

- TIME, TIMEZONES AND CLOCK CORRECTNESS. This is an appointment-scheduling product with statutory California workers'-comp notice deadlines, and twelve recurring jobs pinned to wall-clock times. No area mentions the server timezone, DST transitions (a job at 03:00 local runs twice or zero times once a year), Hangfire's recurring-job timezone parameter, per-appointment timezone storage, or NTP on the VM - which token validation with 15-minute lifetimes, any future TOTP, and every restore-rehearsal timing depends on.

- THE AMBIENT-NULL-TENANT HAZARD HAS NO OWNER. The brief names it explicitly: ABP falls back to the ambient tenant when a job argument carries none, and a worker's ambient tenant is null, which resolves to the HOST database. That is a live cross-boundary data-corruption bug in a PHI system with twelve office-iterating jobs. scaling-topology asks for idempotency, environments asks for test coverage of it - nobody proposes the actual guard (a job filter that refuses to execute a tenant-scoped job with a null resolved tenant, and a host-database assertion that office-shaped tables are never written outside a tenant scope).

- SCHEMA AND APPLICATION ROLLBACK. iac gives a rollback artifact by git SHA; nothing covers rolling back a MIGRATION. EF migrations are forward-only in practice, so redeploying the previous image against a migrated fleet is undefined. No area states an expand/contract discipline for application schema changes (migration-path applies expand/contract only to configuration), and with no staging and manual deploys, 'we shipped a bad migration to eleven offices' has no answer anywhere in 1,000 hours of recommendations.

- BREACH DETECTION, INCIDENT RESPONSE AND FORENSIC READINESS. 45 CFR 164.308(a)(6) security incident procedures is Required; 164.404-410 carries a 60-day notification clock. Observability designs availability alerting. Nobody covers how a breach would be DETECTED, how the set of affected records would be determined, who declares an incident, or forensic log retention - the edge currently keeps no access log at all in the recommendations, and container logs rotate at 10 MB x 5, so an attacker's requests are gone before anyone looks. Audit logs answer 'who touched what' only for authenticated application access.

- REQUIRED ADMINISTRATIVE SAFEGUARDS AND CALIFORNIA LAW. Several areas cite CFR sections; none states that the Required administrative safeguards do not exist - a designated Security Official (164.308(a)(2)), a documented risk analysis (164.308(a)(1)(ii)(A)), sanction policy, and BAAs with the eventual host, the SMTP relay and the Case Tracker partner. And despite the product being California workers' comp, NO AREA CITES CALIFORNIA LAW: CMIA (Civil Code 56 et seq.) and Civ. Code 1798.29/1798.82 breach notification impose obligations that differ from and can exceed HIPAA. A body that argues at length about six-year retention while never opening the state statute has a scope hole.

- PATCHING, EOL AND SUPPLY CHAIN. One SHOULD in scaling-topology asks for a release within twelve months. Nobody owns: Ubuntu 24.04 patching and reboot windows on the single VM, container base-image rebuild cadence, SQL Server 2022 CU cadence, .NET 10 and Angular 20 support windows, an SBOM, or a CVE-response path. Most concretely, scaling-topology STATES as fact that MinIO's open-source server is archived with no patch stream, and no area converts that into a decision - while three other areas build new dependencies on it.

- DATABASE EDITION IS A GO-LIVE BLOCKER WITH NO OWNER. MSSQL_PID is Developer, which the vendor documents as licensed for development and test, not as a production server (Microsoft Learn, editions-and-components-of-sql-server-2022, accessed 2026-08-31). Three areas touch edition constraints in passing; none owns 'choose the edition, run sys.dm_db_persisted_sku_features, and confirm nothing in use is Enterprise-only.' Developer edition silently exposes every Enterprise feature today, and the persisted-SKU query catches only PERSISTED features, not runtime-only ones such as an online index rebuild inside a migration. This is deferred to the platform exercise while being a legal blocker to go-live now.

- HUMAN OPERATING MODEL. Two people, no rota. No area covers: what happens when one developer is on leave (capacity halves) or leaves (the programme ends), knowledge transfer, decision records, or what 'alert' means with no on-call - the dead-man's switch in observability fires into an unspecified channel that nobody is contracted to read at 2am. The honest availability posture is business-hours best-effort, and it should be written down and offered to practices as a commitment rather than left implied.

- DOMAIN AND REGISTRAR CUSTODY. migration-path correctly says do not change registrar or nameservers during the programme, but nobody owns the domain as an asset: who holds the registrar account, registrar lock, expiry monitoring, and DNSSEC custody. It is a single point of total, unrecoverable failure for a system whose entire tenancy model is DNS-derived, and it has no technical control anywhere in the body.

- CONCURRENCY AND PARTIAL-FAILURE IN THE 13-STATE LIFECYCLE. No area treats the domain state machine's correctness: optimistic concurrency when two staff edit one appointment, idempotency of state transitions under retry, and the normal-operation (not just restore-time) case where a database write succeeds and the MinIO write fails or vice versa. availability-dr identifies orphaned objects as a restore artefact; the same hazard exists every day, with no compensating sweep proposed.

## Unjustified complexity

- THE PORTFOLIO ITSELF. 742-1,090 hours of setup and 35-57 hours/month of ongoing obligation against ~40 hours/month shared with feature delivery and an in-flight code-standard exercise. No single area is unreasonable; the sum is roughly 20 months of infrastructure-only work and a steady state that exceeds the budget before anything is built. REALISTIC SUBSTITUTE: a single portfolio-level cut to ~120-160 hours over two quarters, chosen for structural fixes that require zero monthly upkeep, with everything that generates a recurring obligation explicitly deferred and NAMED as deferred so that nobody believes a control exists.

- audit-retention STEP 5 - the monthly per-office export, SHA-256, Object Lock compliance-mode write, chained manifest, read-back verification, then delete, plus an annual cold-restore rehearsal (45-70 h). This is a records-management programme. Its own text says an unverified archive 'is a liability dressed as a control', and verification is exactly the part that decays first. SUBSTITUTE: set a hot retention window the disk supports, write the dated retention policy (which is the artefact the regulation actually requires), and let the immutable off-box DATABASE backups that availability-dr already mandates serve as the long-tail copy. One immutable store, one verification job, not two.

- audit-retention STEP 4 - a third DbContext and third migration set for a per-office _Audit database (25-40 h). It doubles the fleet to ~68 databases, doubles the migration fan-out this team already cannot see the state of, doubles backup and restore units, and adds a third body to a cross-database restore problem that has never been rehearsed once. SUBSTITUTE: keep audit in the office database; take the 10x from Step 1 (narrowing EntityHistorySelectors) and the retention from Step 3. Revisit the split only when a MEASURED office database crosses a written size threshold.

- availability-dr's INSTANCE-CONSISTENT SNAPSHOT PATH - SUSPEND_FOR_SNAPSHOT_BACKUP plus a scripted platform storage snapshot plus BACKUP SERVER WITH METADATA_ONLY (8-16 h plus a permanent operational obligation). It requires a scriptable snapshot API that does not exist yet, and its failure mode is a stuck write-freeze that halts every office simultaneously - a hard failure this team cannot diagnose at 3am, on a code path exercised monthly at best. SUBSTITUTE: per-database full plus log backups off-box, and adopt the area's own better insight - that recovery here must be RECONCILABLE rather than consistent - as the design, not as a consolation.

- availability-dr's 15-MINUTE LOG BACKUP CADENCE ACROSS THE FLEET. 3,264 operations/day at 34 databases, ~6,500 if the audit split lands, each producing an object and msdb history rows, requiring sp_delete_backuphistory scheduling and per-database chain monitoring. SUBSTITUTE: pick the cadence the ALERT can be read at, not the cadence the RPO wish implies - hourly log backups with a written, accepted RPO, and one alert on 'any database whose newest log backup is older than N'. A one-hour RPO nobody has to babysit beats a fifteen-minute RPO with a broken chain.

- migration-path AS WRITTEN (150-190 h at a self-declared 30 h/month for six months). The area itself says that at 15-20 h/month it stretches to 10-14 months and collides with the no-PHI window, and that below 15 h/month it decays into a partially migrated estate that is 'strictly worse than either endpoint'. At the realistic budget it is not executable. SUBSTITUTE: PROMOTE THE AREA'S OWN FALLBACK TO THE RECOMMENDATION - Phase 0 plus Phase 1 plus rebuild-and-reseed onto one new well-provisioned host (~70-90 h) - and delete the dependency-at-a-time Phase 3 entirely. Note that even the fallback is two full months of the total allocation.

- admin-surface LAYER 2 - FallbackPolicy = RequireAuthenticatedUser across BOTH processes (16-26 h), where the cost is discovering every genuinely anonymous endpoint across ABP, OpenIddict, health, anonymous upload and the partner reconcile path. The area concedes it consumes the entire monthly budget and that a half-landed version breaks production sign-in - on a system with one environment and no staging. SUBSTITUTE: ship Layer 1 (admin listener binding, 3-6 h) and Layer 3 as a REPORT rather than a build gate (4-6 h). That is ~10 hours for most of the containment and no risk to sign-in. Then apply FallbackPolicy to the API only, and to the AuthServer only after the inventory report has been clean and stable for a month.

- tenant-lifecycle PHASE 1 - the verified export writer with per-aggregate NDJSON, documents, audit tables, manifest digests and a CI round-trip test (30-45 h plus permanent maintenance against a moving schema). The area itself says it rots first because its correctness silently depends on a schema that keeps changing. SUBSTITUTE: contractual suspend-and-retain as the standing posture (which the area already endorses), plus a DOCUMENTED MANUAL export procedure - native database backup, object-prefix copy, schema script, one manifest - executed by hand at the first real offboarding. Build the automated writer when a customer actually leaves, not against a hypothetical one.

- observability's OTLP INSTRUMENTATION AND STRUCTURED-LOGGING PATH POINTED AT NOTHING (12-16 h). Work that produces no signal until the platform exercise concludes, and may be redone once the destination is known. SUBSTITUTE: do PII-off with a CI grep, retention enforcement, and the three alerts plus dead-man's switch (~25-35 h total), and carry OTLP into the platform exercise as a requirement rather than as pre-built code. Also note the unowned dependency: the dead-man's switch and synthetic probes must run somewhere that is NOT the VM being watched, and no area says where.

- secrets-config TIER 2 + TIER 3 CEREMONY - four-recipient SOPS with an offline escrow identity, an annual witnessed escrow recovery drill, and an annual standby-certificate refresh, both of which must be diarised. Two calendar-triggered rituals for a team with no on-call and no calendar discipline, whose own decay analysis predicts plaintext drift. SUBSTITUTE at this budget: Tier 0 and Tier 1 only (both are code with zero upkeep, and they kill the two documented operational traps), one encrypted copy held independently by each developer, and immediate rotation of everything pasted into chat transcripts. Drop the escrow ceremony until a third person exists.

- capacity-model's WEEKLY FOUR-NUMBER RECORDING AND TREND SHEET. The area itself names the failure exactly: 'collection without reading is the worst state of all - the CSVs exist, so the team believes it has a capacity practice.' A manual weekly ritual with a named owner is the thing this team will not sustain. SUBSTITUTE: one cron df sample with a threshold alert (already required elsewhere), plus a monthly automated message containing the four numbers, a computed slope and a PROJECTED EXHAUSTION DATE. Ship a conclusion, never a dataset.

- iac's QUARTERLY REHEARSED FULL REBUILD (8-10 h/quarter, amortising to 2-3 h/month). Realistically annual for two people. SUBSTITUTE: one rehearsal at build time to validate the runbook, then annual, calendared, with the date of the last successful rebuild published in the same fleet report as everything else. Keep the area's 'structural residue' - fail-fast interpolation, nginx resolve, pinned project name, digest pins - which is genuinely zero-maintenance and is the best value in the body.

- environments STEP 5 (rebuild-on-demand staging on a separate registrable domain, ~24-32 h setup plus permanently maintained DNS-01 automation for a second domain and three more wildcards, plus 4-6 h per activation). Its DNS and certificate automation must be maintained even when the environment does not exist - the exact shape of obligation this team cannot carry. The area already says to drop it below 8 h/month; that condition is met. SUBSTITUTE: keep steps 1, 2 and 4, and treat migration-path's Phase 1 rebuild rehearsal as the only 'second environment' that ever exists.

- THE AGGREGATE PER-OFFICE MONTHLY OBLIGATION. Five areas each add a recurring per-office review: schema-version report, backup outcomes and sizes, audit cleanup confirmation, archive verification, synthetic-prober registration, lifecycle ledger review. At 33 offices that is six sweeps a month. SUBSTITUTE: ONE consolidated fleet report - one row per office, one column per status, emitted by one job, with an alert on ABSENCE and on any red cell. One artefact, one alert, one reader. Every area should be required to render its per-office signal into that single row rather than adding a sweep.

- THE REHEARSAL CALENDAR IS ITSELF UNAFFORDABLE. Counted across the body: weekly automated restore-and-CHECKDB, quarterly timed per-office PITR, quarterly runbook rehearsal, quarterly rebuild, annual clean-host rebuild from off-box artefacts only, annual escrow recovery drill, annual cold-archive restore, plus re-running the growth probe after any audit-scope change. SUBSTITUTE: one automated weekly verification with an absence alert (keep - it is the highest-value item in availability-dr), and exactly ONE human rehearsal per year that is deliberately the clean-host rebuild, because it subsumes the restore, the secrets recovery and the runbook test in a single exercise.

## Vendor-neutrality risks at the portfolio level

- secrets-config: 'Adopt SOPS with age' is a product selection, not a capability requirement, and is stated with pinned versions and release dates as though the decision were settled. The capability is: ciphertext-at-rest for configuration, encrypted to multiple independently held recipients, diffable in version control, decrypted only at deploy. Several tools and at least one platform-native mechanism satisfy that; the platform exercise may change the answer.

- availability-dr: 'Test-DbaLastBackup in dbatools (2.8.4, published 2026-07-31) does exactly this end-to-end and is actively maintained' is presented as the mechanism for the weekly restore-and-CHECKDB, which is one of the two things the area says to implement if nothing else. It should be a requirement ('an unattended process must restore a rotating database to a scratch instance, run an integrity check, and record a dated pass/fail') with the tool as an example of the class.

- environments: 'Testcontainers for .NET (4.14.0, published 2026-08-14)' is named as the mechanism for the entire CI harness - the second-largest item in that area. The requirement is 'ephemeral, disposable real SQL Server and Redis instances created from the build artifact per test run'; the library is one implementation and its lifecycle is now a dependency of the test strategy.

- observability: 'do PHI redaction with Destructurama.Attributed's [NotLogged] and [LogMasked], not Microsoft.Extensions.Compliance.Redaction' is a direct product-versus-product recommendation. The reasoning about call-site coverage is sound and belongs in the record, but the output should be the capability ('redaction must be declared on the model, not per call site, and must be enforced by a test over rendered output') plus the finding, not a package selection.

- state-session: 'use DistributedLock.SqlServer (sp_getapplock) behind the same interface' names a specific library for a correctness-critical control. The capability is 'a lock arbitrated by a single authoritative node that fails closed'; sp_getapplock is the mechanism, the NuGet package is a choice.

- migration-path: 'mc mirror --watch' is named as the object-migration mechanism, and Let's Encrypt is named as the CA whose specific rate limits (5 certificates per identical identifier set per 7 days, 5 authorisation failures per identifier per hour) govern the rehearsal plan. Building the rehearsal schedule around one CA's quota is a de facto CA selection made before the platform exercise. The requirement is 'the certificate authority must permit at least N issuances per week against the rehearsal identifier set, or a staging endpoint must exist.'

- audit-retention: 'Object Lock in COMPLIANCE mode' with 'retain-until' is AWS S3 Object Lock's product vocabulary used as the specification. This one is close to legitimate - the compliance-versus-governance distinction is the load-bearing property and it is correctly argued - but it should be written as the capability ('per-object retention that no administrative or root credential can shorten or remove before expiry') so that a platform offering an equivalent under different terminology is not accidentally screened out, and so that a platform whose 'compliance mode' is weaker is not accidentally accepted on the name.

- CONTINUED RELIANCE ON MINIO IS A VENDOR DECISION MADE BY DEFAULT. scaling-topology states as fact that MinIO's open-source server is archived with no patch stream. migration-path then preserves minio.<base> and its credentials as a design goal, availability-dr proposes SQL Server backup-to-URL against 'the existing S3-compatible endpoint', and admin-surface designs a scoped-credential model for it. Three areas deepen the dependency on a component a fourth says is unmaintained. Not choosing is a choice, and here it is one that puts an internet-exposed, unpatched service in the PHI path.

- network-exposure's health-probe survey (Kubernetes httpHeaders, HAProxy, Traefik, Azure Application Gateway, Google Cloud health checks, AWS ALB/NLB) is correctly framed as evidence of a behaviour class and is the best-executed piece of vendor discipline in the body. The residual risk is that it FUNCTIONS as a pre-emptive vendor screen: it concludes that certain named load balancers cannot probe this application. That conclusion should be re-verified at platform-selection time rather than inherited, because probe-configuration surfaces change and a stale capability claim would silently disqualify a candidate the next exercise is supposed to evaluate on its own terms.

- tenancy-data cites Resource Governor as the mechanism that per-office 'Application Name' would classify for, and MUSTs 'either a mechanism to limit one tenant's resource consumption, or an explicit written acceptance that no such mechanism exists.' Verified: Resource Governor is Enterprise edition only - Standard is 'No' (Microsoft Learn, editions-and-components-of-sql-server-2022, accessed 2026-08-31). Since Developer edition cannot be used in production and the realistic non-Enterprise target is Standard, the requirement resolves to the second branch. The body should record that explicitly instead of leaving a feature reference that reads as available.

- audit-retention and observability both cite 'ABP Commercial has shipped periodic audit-log cleanup since 8.2' and the settings path to enable it. This is incumbent-framework configuration and is legitimate, but it is worth noting that both areas' retention enforcement is entirely dependent on a commercial framework feature toggled through a hidden UI tab - a capability requirement ('retention must be enforceable per database as scheduled configuration without a schema migration', which capacity-model does state) should be the durable form, so that the control survives a framework change.
